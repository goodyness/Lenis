# Requirements Document

## Introduction

The Merchant Onboarding feature enables non-technical African merchants to register on the Lenis Web3 Financial Infrastructure platform, complete identity and business verification, add a crypto wallet address, and begin accepting cryptocurrency payments through shareable payment links and invoices — all without writing any code.

The feature spans a four-step post-registration onboarding wizard, a merchant dashboard, payment link and invoice creation tools, a public-facing checkout page, and an admin interface for reviewing and managing merchant accounts. Blockchain transaction monitoring is out of scope for this spec; this document covers data models, API endpoints, and UI flows only.

---

## Glossary

- **Merchant**: A platform user with `account_type = 'merchant'` who accepts crypto payments from customers.
- **Onboarding_Wizard**: The four-step guided flow that collects personal info, business info, KYC identity documents, and wallet address after a merchant's email is verified.
- **Onboarding_Profile**: The extended merchant record created and populated during the Onboarding_Wizard. Persisted in the `merchant_profiles` database table.
- **KYC**: Know Your Customer identity verification. Either automated via the Dojah API (when `USE_DOJAH=True`) or manual document upload reviewed by an admin (when `USE_DOJAH=False`).
- **KYC_Status**: The current state of a merchant's identity verification. One of: `not_started`, `pending`, `approved`, `rejected`.
- **Merchant_Wallet**: A record storing an EVM-compatible wallet address and network that the merchant has submitted as their receiving address. Stored in the `merchant_wallets` table.
- **EVM_Network**: A supported EVM-compatible blockchain network (Ethereum Mainnet, Base, Polygon, Arbitrum One, Optimism, BNB Smart Chain).
- **Supported_Token**: A cryptocurrency token (native or ERC-20) on a supported EVM_Network that is available for payment acceptance. Configured via environment variables.
- **Payment_Link**: A shareable URL (`/pay/{slug}`) created by a merchant that a customer can open to initiate a crypto payment.
- **Invoice**: A payment request created by a merchant for a specific customer with named line items, sent by email.
- **Invoice_Status**: One of: `draft`, `sent`, `viewed`, `paid`, `overdue`, `cancelled`.
- **Checkout_Page**: The public-facing (unauthenticated) page displayed when a customer opens a Payment_Link URL.
- **Payment_Status**: The current state of a payment transaction. One of: `pending`, `detected`, `confirming`, `confirmed`, `paid`.
- **Slug**: A unique, URL-safe identifier string generated by the system for each Payment_Link.
- **Admin**: A platform user with `account_type = 'admin'` or `account_type = 'superadmin'` who reviews KYC documents and manages merchant accounts.
- **Countries_API**: The REST Countries API (configured via `REST_COUNTRIES_API` in `.env`) used to fetch the list of African countries and their dial codes.
- **Dojah_API**: A third-party KYC service configured via `DOJAH_APP_ID` and `DOJAH_SECRET_KEY` in `.env`, used when `USE_DOJAH=True`.
- **Registration_Document**: A government-issued business registration certificate uploaded by a merchant during Step 2 of the Onboarding_Wizard. PDF or image, max 10 MB.
- **Identity_Document**: A government-issued identity document (NIN slip, national ID card, passport, or driver's license) uploaded during Step 3. PDF or image, max 10 MB.
- **NIN**: Nigeria's National Identification Number, an 11-digit numeric identifier.
- **Onboarding_Status**: A computed summary of a merchant's onboarding progress. One of: `incomplete`, `pending_kyc_review`, `kyc_approved`, `kyc_rejected`.

## Requirements

### Requirement 1: Onboarding Wizard Entry Point

**User Story:** As a merchant who has just verified my email, I want to be directed into a guided setup wizard, so that I can configure my account and start accepting payments.

#### Acceptance Criteria

1. WHEN a merchant with `account_type = 'merchant'` completes email verification, THE Onboarding_Wizard SHALL display automatically as the first post-login page.
2. WHILE a merchant's Onboarding_Profile has `onboarding_complete = False`, THE Onboarding_Wizard SHALL intercept any navigation attempt to routes under the authenticated dashboard (excluding the wizard route and the logout route) and redirect the merchant back to the wizard within 1 second.
3. WHEN a merchant has completed all four wizard steps and submitted the final step successfully, THE System SHALL set `onboarding_complete = True` on the merchant's Onboarding_Profile and redirect the merchant to the dashboard Overview page.
4. IF the final wizard step submission fails due to a server error, THEN THE Onboarding_Wizard SHALL display an inline error message, retain all form field values, and SHALL NOT set `onboarding_complete = True` on the merchant's Onboarding_Profile.
5. WHILE the merchant is on any wizard page, THE Onboarding_Wizard SHALL display the current step number and total step count in the format "Step N of 4".
6. IF a merchant attempts to navigate directly to a wizard step whose index is greater than the highest completed step index plus one, THEN THE Onboarding_Wizard SHALL redirect the merchant to the lowest-numbered incomplete step without displaying the target step.
7. IF a merchant has previously submitted a wizard step, THEN THE Onboarding_Wizard SHALL pre-populate that step's input fields with the previously submitted data when the merchant navigates back to that step.

### Requirement 2: Wizard Step 1 — Personal Information

**User Story:** As a merchant, I want to confirm my personal details and select my country, so that the platform knows where I am based and can auto-populate my phone dial code.

#### Acceptance Criteria

1. THE Onboarding_Wizard SHALL pre-populate the `full_name` field with the value stored on the authenticated merchant's User record.
2. THE Onboarding_Wizard SHALL display the merchant's email address as a read-only field that cannot be edited or submitted as a changed value.
3. WHEN a merchant opens Step 1, THE Onboarding_Wizard SHALL fetch the list of African countries from the Countries_API within a 10-second timeout and populate the country dropdown with the result.
4. IF the Countries_API request fails or does not respond within 10 seconds, THEN THE Onboarding_Wizard SHALL display an inline error message and present a retry button that allows the merchant to re-fetch the country list without refreshing the page.
5. THE Country_Dropdown SHALL support text-based search, updating visible options on each keystroke, so the merchant can filter countries by typing part of the country name.
6. WHEN a merchant selects a country from the Country_Dropdown, THE Onboarding_Wizard SHALL automatically populate the phone dial code prefix in the phone number input with the primary dial code for the selected country.
7. WHEN a merchant submits Step 1, THE System SHALL validate that the full_name field contains between 2 and 100 characters where at least 2 are non-whitespace.
8. WHEN a merchant submits Step 1, THE System SHALL validate that the selected country is a member of the African continent as returned by the Countries_API.
9. WHEN a merchant submits Step 1, THE System SHALL validate that the phone number field, excluding the dial code prefix, is not empty, contains only digits (0–9), spaces, hyphens, and parentheses, and has a total length of 4 to 15 characters.
10. IF Step 1 validation fails, THEN THE Onboarding_Wizard SHALL display a field-level error message adjacent to each invalid field, preserve all previously entered field values, and SHALL NOT navigate away from Step 1.
11. WHEN Step 1 is successfully submitted, THE System SHALL persist the full_name, country, and phone_number to the Onboarding_Profile and advance the merchant to Step 2.
12. IF the Step 1 submission fails due to a server error, THEN THE Onboarding_Wizard SHALL display an inline error message, keep the merchant on Step 1, and preserve all field values.

### Requirement 3: Wizard Step 2 — Business Information

**User Story:** As a merchant, I want to provide my business details, so that customers and admins can identify my organization on the platform.

#### Acceptance Criteria

1. WHEN a merchant submits Step 2, THE System SHALL validate that the business_name field, after trimming leading and trailing whitespace, contains between 2 and 200 characters.
2. WHERE the merchant provides a website_url, THE System SHALL validate that the value begins with `http://` or `https://` and contains a non-empty host segment.
3. WHILE a merchant is on Step 2, THE Onboarding_Wizard SHALL present input fields for the following social media handles: Instagram, Twitter/X, Facebook, LinkedIn, and TikTok, each with a maximum length of 100 characters.
4. WHEN a merchant submits Step 2, THE System SHALL validate that at least one social media handle field contains one or more non-whitespace characters.
5. IF no social media handle contains one or more non-whitespace characters, THEN THE Onboarding_Wizard SHALL display an inline error message stating that at least one social media handle is required.
6. WHILE a merchant is on Step 2, THE Onboarding_Wizard SHALL present a toggle for `is_registered_business` with an explicit default of False (No).
7. WHERE `is_registered_business = True`, THE Onboarding_Wizard SHALL display a file upload input for the Registration_Document.
8. WHERE `is_registered_business` is toggled back to False after a file was previously selected, THE Onboarding_Wizard SHALL clear the previously selected Registration_Document file.
9. WHERE `is_registered_business = True` and the merchant submits Step 2, THE System SHALL validate that a Registration_Document file has been selected.
10. WHEN a Registration_Document is uploaded, THE System SHALL validate that the file's MIME type is one of `application/pdf`, `image/jpeg`, or `image/png`.
11. WHEN a Registration_Document is uploaded, THE System SHALL validate that the file size does not exceed the value of `MAX_UPLOAD_SIZE_MB` megabytes configured in `.env`.
12. IF a Registration_Document fails MIME type or size validation, THEN THE System SHALL return a descriptive error message identifying the violated constraint and reject the upload.
13. WHEN Step 2 is successfully submitted, THE System SHALL persist the business_name, website_url, social_media_handles, is_registered_business, and the uploaded Registration_Document file reference to the Onboarding_Profile and advance the merchant to Step 3.

### Requirement 4: Wizard Step 3 — KYC Identity Verification

**User Story:** As a merchant, I want to verify my identity, so that the platform can comply with its trust and safety requirements before I go live.

#### Acceptance Criteria

1. WHERE `USE_DOJAH = True` in the platform configuration, THE Onboarding_Wizard SHALL initiate the Dojah_API widget to perform identity verification and SHALL store the resulting verification session ID on the Onboarding_Profile.
2. WHERE `USE_DOJAH = False` in the platform configuration, THE Onboarding_Wizard SHALL display a manual document upload flow.
3. WHERE `USE_DOJAH = False` and the merchant's selected country is Nigeria, THE Onboarding_Wizard SHALL display a text input for the NIN and a file upload for the NIN slip or national ID card.
4. WHERE `USE_DOJAH = False` and the merchant's selected country is Nigeria, WHEN the merchant submits Step 3, THE System SHALL validate that the NIN field contains exactly 11 numeric digits with no alphabetic or special characters.
5. WHERE `USE_DOJAH = False` and the merchant's selected country is not Nigeria, THE Onboarding_Wizard SHALL display an Identity_Document type selector with the options: Passport, National ID Card, Driver's License.
6. WHERE `USE_DOJAH = False`, WHEN a merchant submits Step 3, THE System SHALL validate that both an Identity_Document type has been selected and an Identity_Document file has been provided.
7. WHEN an Identity_Document is uploaded, THE System SHALL validate that the file's MIME type is one of `application/pdf`, `image/jpeg`, or `image/png`.
8. WHEN an Identity_Document is uploaded, THE System SHALL validate that the file size does not exceed the value of `MAX_UPLOAD_SIZE_MB` megabytes configured in `.env`.
9. IF an Identity_Document fails MIME type or size validation, THEN THE System SHALL return a descriptive error message identifying whether the MIME type or the file size was the violated constraint, reject the upload, and SHALL NOT store any part of the file.
10. IF a merchant submits Step 3 without providing all required fields (NIN and file for Nigeria; document type and file for non-Nigeria), THEN THE Onboarding_Wizard SHALL display a field-level error message for each missing field and SHALL NOT advance the merchant to Step 4.
11. WHEN Step 3 is successfully submitted with manual documents, THE System SHALL set `kyc_status = 'pending'` on the Onboarding_Profile and store the uploaded Identity_Document file reference.
12. WHERE `USE_DOJAH = True` and the Dojah_API verification returns a success result, THE System SHALL set `kyc_status = 'approved'` on the Onboarding_Profile automatically.
13. WHERE `USE_DOJAH = True` and the Dojah_API verification returns a failure result, THE System SHALL set `kyc_status = 'rejected'` on the Onboarding_Profile and display the Dojah_API failure reason to the merchant.
14. WHERE `USE_DOJAH = True` and the Dojah_API widget fails to load or does not return a result within 30 seconds, THE Onboarding_Wizard SHALL display an error message, allow the merchant to retry, and SHALL NOT advance the merchant to Step 4.
15. WHEN Step 3 is successfully submitted, THE Onboarding_Wizard SHALL advance the merchant to Step 4 regardless of KYC_Status, so wallet setup can proceed in parallel with admin review.

### Requirement 5: Wizard Step 4 — Wallet Setup

**User Story:** As a merchant, I want to add my crypto wallet address, so that I can receive payments directly into my own wallet.

#### Acceptance Criteria

1. THE Onboarding_Wizard SHALL display an explanatory message on Step 4 stating that no wallet app connection is required, no private key or seed phrase will be collected, and that the merchant should paste their public wallet address.
2. WHEN a merchant enters Step 4, THE Onboarding_Wizard SHALL present a network selector listing all supported EVM_Networks from the platform's network configuration with no network pre-selected by default.
3. WHEN a merchant enters Step 4, THE Onboarding_Wizard SHALL present a wallet address text input with a maximum length of 42 characters.
4. WHEN a merchant submits Step 4, THE System SHALL validate that a network has been selected and that the wallet address matches the pattern of a valid EVM address: a `0x` prefix followed by exactly 40 hexadecimal characters (case-insensitive).
5. IF the wallet address fails EVM address validation or no network has been selected, THEN THE Onboarding_Wizard SHALL display an inline error message for each failing field and SHALL NOT advance the merchant.
6. WHEN Step 4 is successfully submitted and the merchant does not already have an active Merchant_Wallet for the selected network, THE System SHALL atomically create a Merchant_Wallet record associating the wallet address, selected network, and merchant's User ID, and set `wallet_added = True` on the Onboarding_Profile.
7. THE System SHALL NOT store, request, or log the merchant's private key, seed phrase, or wallet password at any point.
8. IF the Merchant_Wallet record creation or the Onboarding_Profile update fails due to a server error, THEN THE Onboarding_Wizard SHALL display an inline error message, keep the merchant on Step 4, and preserve all form field values.
9. IF a merchant already has an active Merchant_Wallet for the selected network, THEN THE System SHALL update the existing Merchant_Wallet record with the new address rather than creating a duplicate record.
10. WHEN Step 4 is successfully submitted, THE System SHALL set `onboarding_complete = True` on the Onboarding_Profile and redirect the merchant to the dashboard Overview page.

### Requirement 6: Merchant Dashboard Overview

**User Story:** As a merchant, I want an overview page that shows my payment activity at a glance, so that I can monitor my business without digging through multiple pages.

#### Acceptance Criteria

1. WHEN an authenticated merchant with `onboarding_complete = True` navigates to the dashboard root, THE Dashboard SHALL display the Overview page within 2 seconds.
2. WHEN an authenticated merchant with `onboarding_complete = False` navigates to the dashboard root, THE Dashboard SHALL redirect the merchant to the Onboarding_Wizard.
3. THE Dashboard_Overview SHALL display the merchant's total lifetime received amount aggregated across all Payment_Link and Invoice payments with status `confirmed`, rounded to 2 decimal places with the token symbol.
4. THE Dashboard_Overview SHALL display a single integer value representing the count of payments currently in `pending`, `detected`, or `confirming` status.
5. THE Dashboard_Overview SHALL display the 10 most recent payment transactions in reverse chronological order, showing: payment type (link or invoice), amount rounded to 2 decimal places, token symbol, network name, status, and timestamp in ISO 8601 format.
6. WHEN fewer than 10 payment transactions exist for the merchant, THE Dashboard_Overview SHALL display all available transactions without adding placeholder rows.
7. THE Dashboard_Overview SHALL display a "Create Payment Link" quick-action button that, when clicked, navigates the merchant to the payment link creation form.
8. THE Dashboard_Overview SHALL display a "Create Invoice" quick-action button that, when clicked, navigates the merchant to the invoice creation form.
9. THE Dashboard SHALL include a navigation menu with links to: Overview, Payment Links, Invoices, Transactions, Wallets, Settings, where the active page link is visually distinguished from inactive links.

### Requirement 7: Network and Token Configuration

**User Story:** As a platform operator, I want to configure supported EVM networks and token contract addresses via environment variables, so that the set of accepted networks and tokens can be managed without code changes.

#### Acceptance Criteria

1. THE System SHALL support the following EVM_Networks at launch: Ethereum Mainnet, Base, Polygon, Arbitrum One, Optimism, and BNB Smart Chain.
2. WHEN the System starts up, THE System SHALL read RPC endpoint URLs for each supported EVM_Network from the following environment variables: `ETHEREUM_RPC_URL`, `BASE_RPC_URL`, `POLYGON_RPC_URL`, `ARBITRUM_RPC_URL`, `OPTIMISM_RPC_URL`, `BSC_RPC_URL`.
3. THE System SHALL store each EVM_Network's configuration including: chain ID, network display name, native token symbol, required confirmation count, and estimated block time.
4. THE System SHALL assign the following confirmation thresholds: Ethereum Mainnet = 6 confirmations, Base = 3 confirmations, Polygon = 3 confirmations, Arbitrum One = 3 confirmations, Optimism = 3 confirmations, BNB Smart Chain = 12 confirmations.
5. WHEN the System starts up, THE System SHALL read ERC-20 contract addresses for USDC, USDT, and DAI per network from environment variables using the naming pattern `{NETWORK}_{TOKEN}_CONTRACT` (e.g. `ETHEREUM_USDC_CONTRACT`, `BASE_USDC_CONTRACT`).
6. THE System SHALL support the following Supported_Tokens per network: Ethereum Mainnet — ETH, USDC, USDT, DAI; Base — ETH, USDC, USDT; Polygon — MATIC, USDC, USDT, DAI; Arbitrum One — ETH, USDC, USDT, DAI; Optimism — ETH, USDC, USDT, DAI; BNB Smart Chain — BNB, USDC, USDT.
7. THE System SHALL expose a `GET /networks` endpoint that returns the list of supported EVM_Networks, where each network entry includes: network display name, chain ID, native token symbol, and a list of supported tokens each containing the token symbol and contract address (null for native tokens).
8. IF a required ERC-20 contract address environment variable is missing at startup, THEN THE System SHALL record an error message in the application log identifying the missing variable name and exclude that token from the affected network's Supported_Tokens list.
9. IF a required RPC URL environment variable for a supported EVM_Network is missing at startup, THEN THE System SHALL record an error message in the application log identifying the missing variable name and exclude that network from the active EVM_Networks list.

### Requirement 8: Payment Link Creation

**User Story:** As a merchant, I want to create a shareable payment link with a fixed or flexible amount, so that I can get paid by anyone without giving them my wallet address directly.

#### Acceptance Criteria

1. WHEN an authenticated merchant submits the payment link creation form, THE System SHALL validate that the `title` field contains between 1 and 200 non-whitespace characters.
2. WHEN an authenticated merchant submits the payment link creation form, THE System SHALL require that the `amount_mode` field is one of `fixed` or `flexible`.
3. WHERE `amount_mode = 'fixed'`, WHEN the merchant submits the form, THE System SHALL validate that the `amount` is a positive decimal number with at most 18 decimal places and a value no greater than 999,999,999.99.
4. IF `amount_mode = 'fixed'` and the `amount` fails validation, THEN THE System SHALL return a descriptive error message and SHALL NOT create the Payment_Link.
5. WHEN an authenticated merchant submits the payment link creation form, THE System SHALL present a multi-select input listing all Supported_Tokens across all active EVM_Networks.
6. WHEN a merchant submits the payment link creation form, THE System SHALL validate that at least one Supported_Token has been selected.
7. IF no Supported_Token has been selected, THEN THE System SHALL return a descriptive error message and SHALL NOT create the Payment_Link.
8. WHERE the merchant specifies an `expires_at` date, THE System SHALL validate that `expires_at` is a future timestamp at the time of submission.
9. IF `expires_at` is not a future timestamp, THEN THE System SHALL return a descriptive error message and SHALL NOT create the Payment_Link.
10. WHERE the merchant specifies a `max_uses` value, THE System SHALL validate that `max_uses` is a positive integer no greater than 1,000,000.
11. IF `max_uses` fails validation, THEN THE System SHALL return a descriptive error message and SHALL NOT create the Payment_Link.
12. WHERE the merchant specifies a `redirect_url`, THE System SHALL validate that the value begins with `http://` or `https://` and contains a non-empty host segment.
13. IF `redirect_url` fails validation, THEN THE System SHALL return a descriptive error message and SHALL NOT create the Payment_Link.
14. WHEN a payment link is successfully created, THE System SHALL generate a cryptographically random URL-safe Slug of at least 12 characters. IF a collision with an existing Slug is detected, THE System SHALL regenerate the Slug up to 5 times before returning a server error.
15. WHEN a payment link is successfully created, THE System SHALL store the Payment_Link record with status `active` and return the full payment URL in the format `https://{FRONTEND_ORIGIN}/pay/{slug}`.
16. WHEN a merchant requests QR code generation for a payment link, THE System SHALL return a PNG-format QR code image encoding the payment URL for that link.
17. WHEN a merchant deactivates a payment link, THE System SHALL set the Payment_Link status to `inactive`.
18. WHEN a Payment_Link status is set to `inactive`, THE Checkout_Page SHALL return HTTP 410 for that slug.

### Requirement 9: Payment Link Management

**User Story:** As a merchant, I want to view and manage all my payment links, so that I can track performance and disable links I no longer need.

#### Acceptance Criteria

1. THE System SHALL expose a `GET /merchant/payment-links` endpoint that returns a paginated list of the authenticated merchant's Payment_Links ordered by creation date descending, with a default page size of 20 records and a maximum page size of 100 records.
2. THE Payment_Link list response SHALL include for each link: title, slug, amount_mode, amount, selected tokens, status, expires_at, max_uses, use_count, total_collected, and created_at.
3. IF the requested page number exceeds the total number of available pages, THEN THE System SHALL return an empty results list accompanied by pagination metadata indicating the total record count and total page count.
4. WHILE a Payment_Link has status `active` and `expires_at` is in the past, THE System SHALL treat the link as expired and THE Checkout_Page SHALL return HTTP 410 for that slug.
5. WHILE a Payment_Link has status `active` and `use_count >= max_uses` and `max_uses` is not null, THE System SHALL treat the link as exhausted and THE Checkout_Page SHALL return HTTP 410 for that slug.
6. IF an unauthenticated request is made to `GET /merchant/payment-links`, THEN THE System SHALL return HTTP 401.

### Requirement 10: Invoice Creation and Management

**User Story:** As a merchant, I want to create and send invoices to specific customers with itemised payment requests, so that I can get paid for defined services or goods.

#### Acceptance Criteria

1. WHEN a merchant submits the invoice creation form, THE System SHALL validate that `customer_name` contains between 1 and 200 non-whitespace characters.
2. WHEN a merchant submits the invoice creation form, THE System SHALL validate that `customer_email` is a well-formed email address.
3. WHEN a merchant submits the invoice creation form, THE System SHALL validate that at least one line item has been provided, with a non-empty `description` of at most 500 characters and a positive decimal `amount` with at most 2 decimal places and a value no greater than 999,999.99, and that the total number of line items does not exceed 50.
4. WHEN a merchant submits the invoice creation form, THE System SHALL validate that `due_date` is a future date at the time of submission.
5. WHEN a merchant submits the invoice creation form, THE System SHALL validate that at least one Supported_Token has been selected for payment.
6. WHERE the merchant provides `notes`, THE System SHALL validate that the notes field does not exceed 2000 characters.
7. WHEN an invoice is successfully created with status `draft`, THE System SHALL persist all invoice data but SHALL NOT send an email to the customer.
8. WHEN a merchant explicitly sends a `draft` invoice, THE System SHALL set the invoice status to `sent`, generate an associated Payment_Link for the invoice, and send an email to `customer_email` containing the invoice details and payment URL. IF the email delivery fails, THEN THE System SHALL revert the invoice status to `draft`, deactivate the associated Payment_Link, and notify the merchant of the delivery failure.
9. WHEN an invoice email is opened by the customer and the current invoice status is `sent`, THE System SHALL set the invoice status to `viewed`.
10. WHEN the invoice's associated Payment_Link receives a confirmed payment and the invoice status is `sent`, `viewed`, or `overdue`, THE System SHALL set the invoice status to `paid`.
11. WHEN the current server time passes the invoice `due_date` and the invoice status is `sent` or `viewed`, THE System SHALL set the invoice status to `overdue`.
12. WHEN a merchant cancels an invoice, THE System SHALL set the invoice status to `cancelled` and deactivate the associated Payment_Link.
13. IF a merchant attempts to cancel an invoice with status `paid`, `overdue`, or `cancelled`, THEN THE System SHALL return HTTP 409 and reject the cancellation.
14. THE System SHALL expose a `GET /merchant/invoices` endpoint that returns a paginated list of the authenticated merchant's invoices ordered by creation date descending, with a default page size of 20 and a maximum page size of 100, supporting filter by `status` query parameter.
15. WHEN the invoice's associated Payment_Link receives a confirmed payment but the invoice status is not `sent`, `viewed`, or `overdue`, THE System SHALL NOT change the invoice status.

### Requirement 11: Checkout Page (Public Customer-Facing)

**User Story:** As a customer, I want to open a payment link and see clear instructions for sending crypto, so that I can complete my payment without confusion.

#### Acceptance Criteria

1. THE Checkout_Page at `/pay/{slug}` SHALL be publicly accessible without authentication.
2. WHEN a customer opens `/pay/{slug}`, THE Checkout_Page SHALL display: merchant name, payment title, amount (or an amount entry field if `amount_mode = 'flexible'`), and the list of accepted tokens/networks.
3. IF the slug in the URL does not match any existing Payment_Link record, THEN THE Checkout_Page SHALL display an error message stating the payment link was not found and SHALL NOT render payment input fields.
4. WHERE `amount_mode = 'flexible'`, WHEN the customer submits the amount input, THE Checkout_Page SHALL validate that the entered amount is a positive decimal number between 0.01 and 999,999,999.99 inclusive. IF the amount fails validation, THEN THE Checkout_Page SHALL display an inline error message and SHALL NOT retrieve the merchant's wallet address.
5. WHEN a customer selects a token and network on the Checkout_Page, THE Checkout_Page SHALL retrieve and display the merchant's wallet address for the selected network from the Merchant_Wallet records.
6. IF no Merchant_Wallet record exists for the selected token and network combination, THEN THE Checkout_Page SHALL display an error message and SHALL NOT show a wallet address or QR code.
7. WHEN a customer selects a token and network, THE Checkout_Page SHALL display a QR code encoding the merchant's wallet address and the payment amount for that network.
8. THE Checkout_Page SHALL display a payment instruction message in the format: "Send exactly {amount} {TOKEN} on {NETWORK} to the address below."
9. THE Checkout_Page SHALL display a payment status indicator that reflects the current Payment_Status: PENDING → DETECTED → CONFIRMING → CONFIRMED → PAID, polling for status updates at an interval of no greater than 10 seconds.
10. WHEN the Payment_Status transitions to `paid`, THE Checkout_Page SHALL display a receipt containing: merchant name, amount, token symbol, network name, transaction hash, and confirmation timestamp.
11. THE Checkout_Page SHALL NOT request, display, or store any wallet credentials, private keys, or seed phrases.

### Requirement 12: KYC State Machine

**User Story:** As an admin, I want to review manually uploaded KYC documents and approve or reject them, so that only verified merchants can go live.

#### Acceptance Criteria

1. THE KYC_Status field on an Onboarding_Profile SHALL only transition according to the following valid paths: `not_started` → `pending`; `pending` → `approved`; `pending` → `rejected`; `rejected` → `pending`.
2. IF any actor attempts a KYC_Status transition not listed in Requirement 12.1, THEN THE System SHALL return HTTP 409 and reject the transition.
3. WHEN an admin approves a KYC submission, THE System SHALL set `kyc_status = 'approved'`, record the reviewing admin's User ID and the approval timestamp on the Onboarding_Profile, and log the action to the AuditLog with `event_type = 'kyc_approved'`.
4. WHEN an admin rejects a KYC submission, THE System SHALL require a `rejection_reason` string of between 1 and 500 characters, set `kyc_status = 'rejected'`, record the rejection reason, the reviewing admin's User ID and the rejection timestamp on the Onboarding_Profile, and log the action to the AuditLog with `event_type = 'kyc_rejected'`.
5. IF the `rejection_reason` provided is empty or exceeds 500 characters, THEN THE System SHALL return a descriptive error message and SHALL NOT change the Onboarding_Profile.
6. WHEN a KYC submission is approved, THE System SHALL dispatch a Celery task to send a notification email to the merchant informing them of the approval decision.
7. WHEN a KYC submission is rejected, THE System SHALL dispatch a Celery task to send a notification email to the merchant informing them of the rejection decision and SHALL include the rejection reason in the notification email.
8. WHEN a merchant resubmits KYC documents after a rejection, THE System SHALL transition `kyc_status` from `rejected` to `pending` and clear the previous rejection reason.

### Requirement 13: Merchant Wallet Management

**User Story:** As a merchant, I want to manage my wallet addresses after onboarding, so that I can update or add wallets for different networks.

#### Acceptance Criteria

1. WHEN an authenticated merchant calls `GET /merchant/wallets`, THE System SHALL return all Merchant_Wallet records associated with that merchant, with a maximum of 100 records per response.
2. WHEN an authenticated merchant calls `POST /merchant/wallets`, THE System SHALL validate that the request contains a wallet address and a network field that is a non-empty string of at most 64 characters.
3. WHEN a new Merchant_Wallet is submitted, THE System SHALL validate that the wallet address matches the EVM address pattern: `0x` prefix followed by exactly 40 hexadecimal characters. IF the address fails validation, THEN THE System SHALL return HTTP 422 and SHALL NOT create any record.
4. IF a merchant already has a Merchant_Wallet with status `active` or `pending` for the same network, THEN THE System SHALL return HTTP 409 and reject the duplicate submission.
5. WHEN an authenticated merchant calls `DELETE /merchant/wallets/{wallet_id}`, THE System SHALL verify that the specified wallet_id belongs to the authenticated merchant. IF the wallet_id does not belong to the merchant, THEN THE System SHALL return HTTP 404.
6. IF a merchant attempts to delete a Merchant_Wallet that is the only wallet on record for that merchant and is associated with Payment_Links in status `active` or `pending`, THEN THE System SHALL return HTTP 409 and reject the deletion.

### Requirement 14: Admin Merchant Management

**User Story:** As an admin, I want a management interface for all merchant accounts, so that I can monitor onboarding status, review KYC, and take enforcement actions.

#### Acceptance Criteria

1. THE System SHALL expose a `GET /admin/merchants` endpoint accessible only to users with `account_type = 'admin'` or `account_type = 'superadmin'`, returning a paginated list of all merchant accounts with their Onboarding_Status, KYC_Status, and wallet count, with a default page size of 20 records and a maximum page size of 100 records, using `page` and `page_size` query parameters.
2. THE System SHALL expose a `GET /admin/merchants/{user_id}` endpoint returning the full Onboarding_Profile, Merchant_Wallet list, KYC document references, payment link count, invoice count, and total confirmed transaction volume expressed as a numeric amount with currency code for the specified merchant.
3. THE System SHALL expose a `GET /admin/merchants/{user_id}/kyc-documents` endpoint that returns signed download URLs valid for between 15 and 60 minutes, or file data for the Identity_Document and Registration_Document associated with the specified merchant.
4. THE System SHALL expose a `POST /admin/merchants/{user_id}/kyc/approve` endpoint. WHEN called, THE System SHALL verify that the merchant's `kyc_status` is `pending` before transitioning it to `approved` per the rules in Requirement 12.
5. THE System SHALL expose a `POST /admin/merchants/{user_id}/kyc/reject` endpoint that accepts a `rejection_reason` string of between 1 and 500 non-empty characters and transitions the merchant's `kyc_status` to `rejected` per the rules in Requirement 12.
6. WHEN an admin suspends a merchant via `POST /admin/merchants/{user_id}/suspend`, THE System SHALL set the merchant User's `status = 'suspended'`, set all active Payment_Links for that merchant to status `suspended_by_admin`, and log the action to AuditLog with `event_type = 'merchant_suspended'`.
7. IF a merchant's User `status` is already `suspended` when `POST /admin/merchants/{user_id}/suspend` is called, THEN THE System SHALL return an error, make no changes to any Payment_Link, and SHALL NOT write an AuditLog entry.
8. WHEN an admin unsuspends a merchant via `POST /admin/merchants/{user_id}/unsuspend`, THE System SHALL set the merchant User's `status = 'active'`, reactivate only the Payment_Links whose status was set to `suspended_by_admin` during the most recent suspension, and log the action to AuditLog with `event_type = 'merchant_unsuspended'`.
9. IF a non-admin user attempts to access any `/admin/merchants` endpoint, THEN THE System SHALL return HTTP 403.
10. WHEN an admin action against a merchant completes, THE System SHALL log the action to the AuditLog with the admin's User ID as `actor_id`, the merchant's User ID as `target_id`, the action name as `event_type`, and an `outcome` of `success` or `failure`, regardless of whether the underlying merchant record was modified.

### Requirement 15: File Storage

**User Story:** As a platform operator, I want uploaded documents stored reliably and retrieved securely, so that KYC documents are protected and available for admin review.

#### Acceptance Criteria

1. THE System SHALL store uploaded files using the storage backend indicated by the `UPLOAD_STORAGE` environment variable: `local` for filesystem storage or `s3` for AWS S3.
2. WHERE `UPLOAD_STORAGE = 's3'`, THE System SHALL use the `AWS_S3_BUCKET`, `AWS_ACCESS_KEY_ID`, and `AWS_SECRET_ACCESS_KEY` environment variables to authenticate with S3.
3. THE System SHALL store each uploaded file under a path that includes the merchant's User ID and a UUID as the unique file identifier to prevent path collisions.
4. THE System SHALL NOT expose raw file storage paths or S3 URLs directly in API responses accessible to merchants.
5. THE System SHALL gate file download access by admin authentication, requiring a valid admin session before serving or generating download links for any uploaded file.
6. WHERE `UPLOAD_STORAGE = 's3'` and an admin requests a KYC document download, THE System SHALL generate a pre-signed URL valid for a maximum of 15 minutes.
7. IF the storage backend is unavailable during a file upload or download request, THEN THE System SHALL return an error to the caller and SHALL NOT create any partial file record.
8. WHEN a file is uploaded, THE System SHALL validate that the file's declared MIME type matches the file's actual content type as determined by server-side inspection, and SHALL reject uploads where the content is PDF, JPEG, or PNG but does not match the declared type, or where the file size exceeds 10 MB.

### Requirement 16: Onboarding Progress API

**User Story:** As a frontend engineer, I want a single endpoint that returns the merchant's current onboarding state, so that the wizard can resume from the correct step after a page refresh.

#### Acceptance Criteria

1. THE System SHALL expose a `GET /merchant/onboarding-status` endpoint returning the authenticated merchant's current Onboarding_Status, current wizard step index (1–4), `onboarding_complete` flag, `kyc_status`, and `wallet_added` flag.
2. WHEN a merchant refreshes the browser during the wizard, THE Onboarding_Wizard SHALL call `GET /merchant/onboarding-status` and resume from the lowest-numbered step whose required fields are not fully submitted, falling back to step 1 if all steps are complete or no prior data exists.
3. IF an unauthenticated request is made to `GET /merchant/onboarding-status`, THEN THE System SHALL return an authentication failure error without including any onboarding data in the response.
4. THE System SHALL expose a `PATCH /merchant/onboarding/{step}` endpoint for steps 1–4 that accepts the step's form data, validates it, persists it, and returns the updated Onboarding_Status.
5. IF a `PATCH /merchant/onboarding/{step}` request is made with a step value outside the range 1–4, THEN THE System SHALL return an error identifying the invalid step value and SHALL NOT persist any data.
6. IF a merchant calls `PATCH /merchant/onboarding/{step}` for a step number greater than `current_step + 1`, THEN THE System SHALL return an error indicating the step cannot be skipped and SHALL NOT persist any data.
7. IF a `PATCH /merchant/onboarding/{step}` request contains invalid form data, THEN THE System SHALL return an error identifying each invalid field and SHALL NOT persist any data.
